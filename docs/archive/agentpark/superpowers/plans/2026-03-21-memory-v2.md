# Memory V2: Session Summaries, Embeddings, Agent-Memory Tools

> Konzeptioneller Plan — klaert wie Memory in Mycelos funktionieren soll.

---

## Aktueller Stand

- `memory_entries` in SQLite: Key-Value, 4 Scopes (system, agent, shared, session)
- Sessions als JSONL-Files, kein automatisches Memory-Update
- Agents haben keine Memory-Tools
- Kein Embedding/Semantic Search
- Memory wird nicht in System-Prompt injiziert (ausser user.name)

## Ziel

```
Session laeuft
    ↓
Agent kann memory.write nutzen (wichtige Fakten)
    ↓
Session endet (exit/timeout)
    ↓
Memory Updater (Background, Haiku — billig)
    "Was war wichtig in dieser Session?"
    → Extrahiert: Praeferenzen, Entscheidungen, Kontext
    → Schreibt in memory_entries
    ↓
Naechste Session
    ↓
System-Prompt enthaelt relevantes Memory:
    <memory>
    User: Arbeitet an Mycelos Agent OS
    Preferences: Mag Markdown, spricht Deutsch
    Recent: Hat AI News Workflow eingerichtet
    </memory>
```

## Drei Saeulen

### 1. Agent Memory Tools

Agents koennen waehrend der Ausfuehrung ins Memory schreiben/lesen:

```python
MEMORY_TOOLS = [
    {
        "name": "memory_read",
        "description": "Read a fact from memory",
        "parameters": {"key": "str — what to look up"},
    },
    {
        "name": "memory_write",
        "description": "Remember an important fact about the user or context",
        "parameters": {
            "key": "str — category (e.g. 'user.preference.format')",
            "value": "str — the fact to remember",
        },
    },
]
```

Nutzung im Chat:
```
User: "Ich mag keine Emojis in den Zusammenfassungen"
Mycelos: [memory_write("user.preference.no_emojis", "true")]
        "Alles klar, keine Emojis. Ich merke mir das!"
```

### 2. Session Summary (automatisch)

**Trigger:** Session-Ende erkennen
- User tippt `exit`/`quit` → sofort
- Timeout: 30 Min keine Nachricht → Cron-Job
- Gateway: SSE disconnect
- App Shutdown: Shutdown-Hook

**Extraktion:** LLM-Call (Haiku, billig) mit der Session-History:

```
Prompt: "Analysiere diese Conversation. Extrahiere:
1. Neue User-Praeferenzen (was mag/will der User?)
2. Wichtige Entscheidungen (was wurde beschlossen?)
3. Kontext-Updates (woran arbeitet der User?)
4. Agent-spezifische Infos (was hat ein Agent gelernt?)

Antworte als JSON:
{
  'preferences': [{'key': '...', 'value': '...'}],
  'decisions': [{'key': '...', 'value': '...'}],
  'context': [{'key': '...', 'value': '...'}],
  'agent_memories': [{'agent_id': '...', 'key': '...', 'value': '...'}]
}"
```

DeerFlow-Ansatz: Debounced (30s), batched, async. Wir koennen das beim Session-Ende synchron machen (einfacher) oder als Cron-Job (braucht Huey).

### 3. Memory Injection in System-Prompt

Bei jeder neuen Session/Message werden relevante Memory-Eintraege in den Prompt injiziert:

**Ohne Embeddings (Phase 1):** Alle System-Scope Eintraege laden, nach Recency sortieren, top N nehmen.

**Mit Embeddings (Phase 2):** User-Message embedden → aehnliche Memory-Eintraege finden → die relevantesten injizieren.

```python
def inject_memory(app, user_id, message=None):
    """Build memory context for system prompt injection."""
    entries = []

    # System-scope: always include (user prefs, context)
    system_entries = app.memory.search(user_id, "system", "")
    for e in system_entries[:20]:
        entries.append(f"- {e['key']}: {e['value']}")

    # If embeddings available: semantic search
    if message and app.embedding_available():
        similar = app.memory.semantic_search(user_id, message, limit=5)
        for e in similar:
            entries.append(f"- [relevant] {e['key']}: {e['value']}")

    if not entries:
        return ""

    return "<memory>\n" + "\n".join(entries) + "\n</memory>"
```

## Embedding-Konfiguration

### Bei `mycelos init`: Embedding-Modell konfigurieren

```
--- Embedding Model (optional) ---

Fuer semantische Suche im Memory. Optional — ohne Embeddings
funktioniert Memory mit Keyword-Suche.

  (1) OpenAI text-embedding-3-small  $0.02/1M tokens, 1536 dims
  (2) Voyage voyage-3.5-lite         $0.02/1M tokens (Anthropic-Partner)
  (3) Gemini gemini-embedding-001    $0.15/1M tokens, 3072 dims
  (4) Ollama nomic-embed-text        kostenlos (lokal)
  (5) Kein Embedding (Keyword-Suche)

Embedding Model [5]:
```

### Provider-Verfuegbarkeit

| Provider | Embedding-Modell | Kosten | Braucht eigenen Key? |
|----------|-----------------|--------|---------------------|
| OpenAI | text-embedding-3-small | $0.02/1M | Ja (OPENAI_API_KEY) |
| Voyage | voyage-3.5-lite | $0.02/1M | Ja (VOYAGE_API_KEY) |
| Gemini | gemini-embedding-001 | $0.15/1M | Ja (GEMINI_API_KEY) |
| Ollama | nomic-embed-text | $0.00 | Nein (lokal) |
| Anthropic | — | — | Kein eigenes Modell |

**Smart Default:** Wenn User schon OpenAI Key hat → `text-embedding-3-small`.
Wenn nur Anthropic → Voyage vorschlagen. Wenn Ollama → `nomic-embed-text`.

### Embedding-Storage

```sql
-- Neue Spalte in memory_entries
ALTER TABLE memory_entries ADD COLUMN embedding BLOB;
-- Oder separate Tabelle:
CREATE TABLE IF NOT EXISTS memory_embeddings (
    memory_id INTEGER REFERENCES memory_entries(id),
    embedding BLOB NOT NULL,  -- Float32 array
    model TEXT NOT NULL,       -- welches Embedding-Modell
    PRIMARY KEY (memory_id)
);
```

Fuer Aehnlichkeitssuche: SQLite hat kein natives Vector Search.
Optionen:
- **sqlite-vss** Extension (C, muss kompiliert werden)
- **Brute-Force** in Python (klein genug bei <1000 Eintraegen)
- **LanceDB** (wie OpenClaw, separate DB)

Vorschlag: Phase 1 ohne Embeddings (Keyword-Suche reicht bei wenig Memory).
Phase 2 mit LanceDB oder sqlite-vss wenn Memory waechst.

## Session-Ende Detection

### Im Chat (Direct Mode)

```python
# In chat_cmd.py — bei exit/quit/q:
if user_input.lower() in {"exit", "quit", "q"}:
    _trigger_session_summary(app, session_id)
    break
```

### Im Gateway (SSE Mode)

```python
# In routes.py — SSE disconnect detection:
# FastAPI/Starlette hat keinen direkten disconnect-Hook fuer SSE.
# Loesung: Session-Timeout per Cron-Job.
```

### Per Cron-Job (braucht Scheduler)

```python
# Alle 5 Minuten pruefen:
def check_stale_sessions():
    sessions = app.session_store.list_sessions()
    for s in sessions:
        last_msg_time = s.get("timestamp")
        if is_older_than(last_msg_time, minutes=30):
            if not already_summarized(s["session_id"]):
                trigger_session_summary(app, s["session_id"])
```

### Ohne Scheduler (Phase 1): Beim naechsten Session-Start

```python
# In ChatService.create_session():
# Prüfe ob die letzte Session ein Summary hat
last_session = app.session_store.get_latest_session()
if last_session and not _has_summary(last_session):
    _trigger_session_summary(app, last_session)
```

Das ist der DeerFlow-Ansatz: Lazy — Summary wird erst erstellt wenn es gebraucht wird.

## Implementierungs-Phasen

### Phase 1 (ohne Scheduler, ohne Embeddings)

1. **Memory-Tools** fuer den Chat-Agent (memory_read, memory_write)
2. **Memory-Injection** in System-Prompt (alle System-Scope Eintraege)
3. **Session Summary** beim naechsten Session-Start (lazy)
4. **Init: Embedding-Modell konfigurieren** (optional, vorbereitet)

### Phase 2 (mit Scheduler)

5. **Cron-Job** fuer Session-Summary (alle 5 Min stale Sessions pruefen)
6. **Cron-Job** fuer Memory-Cleanup (abgelaufene Eintraege loeschen)

### Phase 3 (mit Embeddings)

7. **Embedding bei Memory-Write** — jeder Eintrag wird embedded
8. **Semantic Search** bei Memory-Injection (relevanteste Eintraege fuer den Kontext)
9. **LanceDB oder sqlite-vss** fuer Vector-Suche
